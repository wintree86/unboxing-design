# 피드백 적용과 작업 범위

제작 전에 하네스 `status`의 `production_allowed_by_candidate`, `expansion_allowed`, 원문 이벤트를 읽는다. 하네스가 없는 첫 작업도 실제 사용자 요청의 범위를 먼저 따른다. 직접 Pencil 도구 호출은 CLI가 물리적으로 막지 못하므로 생성 전에 이 절차를 지키고, 생성 뒤 실제 노드를 presentation에 등록한다.

| 요청 | 기본 산출물 |
|---|---|
| 새 방향 탐색 | 대표 화면의 독립적인 두 방향. 사용자 지정 범위 우선 |
| 선택한 방향 수정 | 선택 버전 하나의 전후. 실제 상충하는 해법만 추가 비교 |
| 원인 조사·제작 중지 | 자료·실제 화면·기록 분석과 수정안 문서. 새 화면/색상 실험/프로토타입 없음 |
| 같은 지적의 재거절 | 이전 가설과 반증을 재검토. 이름·팔레트만 바꿔 재시작하지 않음 |

원문 피드백은 즉시 기록한다. 자유문장을 키워드로 판정하지 말고 제작자가 맥락과 화면으로 분류한다. 사용자가 보드에서 명시한 요청 종류는 그 원문과 함께 저장할 수 있다. 후보가 불명확해도 전체 실행 피드백으로 접수하고, 오래된 버전은 역사로 보존한다. 원인 조사 모드는 실제 제작 재개 지시로만 해제한다.

기존 brief/revision에 짧게 다음을 적는다. 새로운 장문 기획서나 매번 승인 질문을 요구하지 않는다.

- 원문 이벤트 ID·대상 버전과 실제 관찰 경로.
- 관찰한 문제, 제작자의 해석 가설, 바꿀 **화면 관계**와 실제 노드.
- 기존 선택에서 유지할 조건과 사용자 원문. 사용자가 고정하지 않은 색·좌표까지 영구 제약으로 확대하지 않는다.
- 오해 방지/반증 근거, 반영하지 않은 부분과 이유, 남은 문제.
- 같은 콘텐츠·상태의 전후 자료. 객관적 결함의 측정과 미적 수정의 검토용 반영을 구분한다.

예를 들어 여백 지적은 정보 묶음과 영역 비중을 먼저 살핀다. 버튼 높이만 줄인 것을 공간 관계 해결로 처리하지 않는다. ‘책처럼’을 종이색·명조체 의무로, ‘흰색이 없다’를 픽셀 수로 반박하거나 전면 흰 배경 확정으로 바꾸지 않는다. 실제로 상충하는 중요한 결정만 질문한다.

후속 변경 요청·거절은 이전 선택을 역사로 보존하면서 해당 범위의 진행 근거를 재검토하게 한다. 미적 수정은 적용 기록과 현재 시각 검토를 연결한 뒤 기존 방향 선택 흐름으로 제시한다. 피드백 문장마다 별도 사용자 승인 단계를 만들지 않는다. 보고는 **이번 지적에 대한 대응 → 실제 전후 → 남은 문제 → 기술 수치** 순서로 한다.
