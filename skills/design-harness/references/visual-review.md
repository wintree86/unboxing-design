# 대표 화면의 시각 검토와 확장

이 문서는 design-bot 산출물을 검토하는 에이전트의 작업 절차다. CLI의 수치 검사와 별개이며 현재 실행기가 이 문서의 의미·미적 품질을 자동 판정한다고 보고하지 않는다. 같은 생성자가 수행하면 자기 검토로 표시한다. 별도 검토자가 실제 참여한 경우에만 독립 검토라고 쓴다.

## 비교 준비

새 방향 또는 품질 거절 후에는 [대표 화면 제작](../../design-bot/references/representative-study.md)의 근거를 읽는다. 대표 screen/state/viewport, 콘텐츠·행동, 이전 버전, 사용자 거절 원문을 고정한다. 기본 첫 비교는 한 화면의 독립적인 두 방향이며 사용자 지정 범위는 우선한다. 나머지 화면을 먼저 제작하지 않는다.

사용자에게 보이는 비교 패키지에는 다음을 연결한다.

- 실제로 본 원본 레퍼런스와 영역·비례·서체·간격 분석.
- 편집 가능한 구성 연구와 원본 대비 차이, 제품으로 바꾼 이유.
- 같은 배율의 이전/새 대표 화면과 필요 부위 확대.
- 채택 원리 → 제품 구성 → 실제 노드, 전후 변경과 장단점.
- 현재 범위의 기술 측정, 미측정 항목, 아래 시각 검토와 다음 행동.

근거는 `docs/design-harness/{run-id}/visual-review.md`에 기록하고 brief에서 연결한다. 비교 보드 UI가 이 자료를 직접 표시하지 못하면 동일 실행의 보충 보드/문서로 함께 제시한다. 근거가 없는데 실행기나 보드 기능을 추가해 해결한 것으로 대체하지 않는다.

## 화면에 근거한 비평

| 축 | 실제로 볼 것 | 기록 방식 |
|---|---|---|
| 위계 | 첫 시선·두 번째 정보·주 행동의 우선순위 | 해당 노드와 상대 비중, 의도와의 차이 |
| 밀도·공간 | 강약, 여백과 압축 구간, 노출량과 접근 경로 | 렌더 영역/노출 수/거리와 가독성에 대한 판단을 분리 |
| 타이포그래피 | 크기 관계, 굵기, 줄바꿈, 숫자·보조 정보의 역할 | 실제 텍스트와 확대 부위, 선언 폰트와 실관찰을 구분 |
| 디테일 | 정렬, 간격, 아이콘·선·표면·선택 상태의 일관성 | 문제 위치 → 사용자에게 보이는 영향 → 수정 제안 |
| 레퍼런스 번역 | 원본의 구성 원리가 우리 콘텐츠에서 작동하는지 | 원본 영역 → 연구본 → 제품 노드, 채택/변형/배제 이유 |
| 후보 차이·손실 | 표현·읽기 흐름·행동의 실제 차이 | 얻은 점과 잃은 점. 색만 다른 안은 그렇게 명시 |

‘세련됨 부족’, ‘85점’ 같은 총평으로 끝내지 않는다. 예: ‘보조 일정 제목과 주 일정 제목이 같은 크기여서 먼저 볼 일정이 드러나지 않는다 → 주 일정 영역의 비중과 제목 관계를 수정한다.’ 반대로 단순함 자체를 결함으로 보지 않는다. 제품 과업과 요구한 인상을 판단 기준으로 삼는다.

비율·거리·대비·행동 크기 등은 실제 관찰값으로 기록한다. 정량값이 아름다움·창의성의 정답은 아니다. 새로운 미적 점수·임계값을 만들어 통과시키지 않는다. 기존 기술 기준은 유지한다.

## 다음 행동

| 관찰 결과 | 행동 |
|---|---|
| 분석/연구/전후 근거가 비어 있음 | 누락된 제작·관찰을 먼저 수행. 선택 준비 완료라고 보고하지 않음 |
| 두 방향 모두 거절 이유를 반복함 | 같은 대표 화면 재작업. 후보 수나 화면 수를 늘려 덮지 않음 |
| 한 방향만 설득력이 있음 | 장점과 남은 약점을 밝히고 기존 선택 단계에서 추천. 자동 선택으로 쓰지 않음 |
| 기술 측정 통과, 시각 검토의 중대한 문제가 남음 | 시각 문제 수정. 측정 통과와 미적 적합성을 분리 보고 |
| 비교 준비 완료, 사용자 무응답 | 결정 미정 유지. 독립적인 검증·문서 작업은 계속하고 전체 확장은 하지 않음 |
| 실제 방향 선택 또는 해당 범위의 명시적 위임 | 선택한 원리를 추출해 나머지 화면 확장. 비선택 후보는 보존 |

기존 CLI의 `feedback` 저장은 자동 재작업 전환을 보장하지 않는다. 원문을 기록하고 선택 철회/변경이 있으면 해당 방향 문서·brief의 현재 결정 범위를 갱신해 `refresh`한다. 그 뒤 `status`에서 이전 선택이 남았는지 확인한다. 기술 상태가 `awaiting_direction`이어도 최신 거절 근거가 있으면 선택된 것으로 취급하거나 확장하지 않는다. 상태 파일을 직접 편집해 결정을 만들어내지 않는다.

수정은 기존 자동 수정 예산을 따른다. 예산 소진을 피하려고 새 run을 반복 생성하지 않는다. 사용자 요청으로 재시작했으면 이전 실행·사용한 수정 횟수·새 범위를 명시한다. 같은 생성자의 비평과 사용자 선택은 최종 독립 리뷰를 대신하지 않는다.
