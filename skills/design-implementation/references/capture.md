# 실제 앱 캡처와 차이 조사

## 비교 순서

1. 같은 승인 버전의 기준 PNG와 편집 원본 조회를 묶는다. 데이터가 있는 홈과 빈 서재, 도구 열린 상태와 닫힌 상태를 혼합하지 않는다.
2. 실제 앱을 같은 fixture·locale·text scale·viewport·DPR·scroll 상태로 실행한다. 상태 준비를 위해 사용자 데이터를 덮거나 기존 시뮬레이터를 초기화하지 않는다. 별도 fixture/임시 서재를 사용한다.
3. 전체 화면 PNG를 저장하고 화면별 주요 영역/행동을 식별한다. 전체 프레임을 임의 확대·크롭해 위치 오차를 숨기지 않는다. OS 상태바 등 비교 제외 영역이 있으면 기준 계약에 명시한다.
4. 렌더 결과에서 측정한다. Flutter는 RenderBox/RenderParagraph의 실제 크기와 global 좌표, 브라우저는 getBoundingClientRect와 computed style, 네이티브는 접근성 프레임/화면 픽셀을 사용한다. 디자인 노드·CSS 설정·Dart 상수를 actual 측정으로 쓰지 않는다. 실제 폰트 자산과 글리프 표시도 관찰한다.
5. 동일 프레임의 원본/실제/오버레이를 보고 위계·밀도·서체·이미지/표면·컨트롤 디테일을 검토한다. 그라데이션·그림자·자산의 부재를 글자 잘림 0으로 통과시키지 않는다. 자동 수치와 관찰한 의미를 분리한다.
6. 차이를 `누락`, `구성 변경`, `위치/크기`, `타이포`, `색/표면/자산`, `동작/상태`, `미검증`으로 기록한다. 원인이 공통 컴포넌트이면 모든 소비 화면을 조사한다. 화면을 줄였으면 부분 완료로 남긴다.

## 구현 프레임워크

- Flutter: 디자인의 고유 컴포넌트·자산을 토큰에 연결한다. 기본 Material/Cupertino 선택 상태·패딩·모양·최소 크기도 실제 화면에서 비교한다. 의도적 긴 문구 축약과 번역 UI 문구 누락을 구분한다. Dart 변경 뒤 dart analyze와 관련 회귀를 실행한다.
- Web: 실제 브라우저의 폰트 로드 완료와 이미지 로드 결과를 확인한 뒤 측정한다. computed style만으로 실제 픽셀의 대비·그라데이션 적합성을 주장하지 않는다.
- Native: 창/시스템 UI와 콘텐츠 영역을 구분한다. 작은 Mac 창을 휴대폰처럼 바꾸는 등 플랫폼 고유 탐색을 임의로 대체하지 않는다.

## 검증 경계

검사기는 캡처의 PNG 크기, 파일/코드 현재성, 같은 비교 조건, 요구된 요소·문구·행동·위계, 제출한 속성과 geometry 차이를 확인한다. 캡처가 실제 실행에서 생성되었는지, 측정자가 화면을 빠짐없이 매핑했는지, 사용자 지시가 진짜인지, 사람에게 동일한 인상인지는 자동 인증하지 않는다. 해당 부분은 관찰 근거와 리뷰로 남긴다. 기능 테스트나 검사기 성공을 사용자 최종 수용으로 쓰지 않는다.

제품에 이미 승인된 디자인이 있으면 브랜드/배치/컨트롤의 새 미적 방향을 만들지 않는다. 기술상 충돌은 원래 화면과 작동 가능한 변경안을 구체적으로 비교해 기존 사용자 결정 절차로 처리한다. 검증의 모든 실행마다 새 승인을 요구하지 않는다.
